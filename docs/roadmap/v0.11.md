# Roadmap: v0.11 (in progress)

The current milestone, kept here with its baseline and plan; [the roadmap](../ROADMAP.md)
holds its summary.

## v0.11 — Imports faster than CPython

v0.10's CI benchmark job put pydantic's import at 0.93x CPython (455.7M instructions vs
442.9M); the rest is a 10.5 MB extension to load, ~8.8M instructions of libpython object
creation (functions, classes, forwarders, signatures) and ~296 fallback chunks run at
import. v0.11 makes importing compiled packages at least as fast as importing their sources,
then faster, without changing what Python code can observe.

Accept:
1. **pydantic import >= 1.0x**, then **>= 1.2x** as a stretch: median of the CI benchmark
   job (`bench.yml`) for `import pydantic; from pydantic import BaseModel`, compiled tree vs
   CPython from `.pyc`, same pydantic-core wheel; its suite fails no test that passes
   against its sources.
2. **Smaller, faster-loading extensions:** LTO across a whole-package build's modules,
   identical-code folding and cold sections for import-only, error and fallback paths are
   each measured on the pydantic and mistune extensions; what pays ships, the rest is
   recorded with its numbers; the pydantic extension's size and load-time relocations are
   measured and reduced, with no runtime instruction-count regression on the CI bounds.
   **Measured 2026-10-30** (x86_64, glibc 2.39, GNU ld 2.42; callgrind/cachegrind with
   `PYTHONHASHSEED=0`). Shipped: ELF extensions built for a glibc >= 2.36, with a linker
   that packs them (a probe link decides: GNU ld 2.42 does on x86-64 and ignores the flag
   on aarch64), link with `-z pack-relative-relocs` -- pydantic's extension 10,751,680 -> 10,256,144 bytes
   (-4.6%), relocation entries 21,222 -> 349 (`.rela.dyn` 503,712 bytes -> 2,760 plus a
   5,160-byte `.relr.dyn`), `dlopen` 1.214M -> 1.167M instructions; mistune's 3,934,696 ->
   3,717,680 bytes (-5.5%), 9,395 -> 348 entries, `dlopen` 472K -> 460K. An extension's
   module body is `cold` (`.text.unlikely`, away from what runs after import): simulated
   L1i misses on mistune's hot path -2.0% per call. The CI instruction bounds are
   unchanged to the digit (diff-match-patch 131.29M, pypng 13.79M, mistune 57.87M,
   pystache 0.47M per call), and so is the build: no compile step changed. Loading the
   extension is not where the import goes: `dlopen` is 0.3% of pydantic's 376M-instruction
   import, and the import's instruction count and wall time are unchanged within noise.
   Rejected: LTO (members' optimized bitcode linked, `constmerge,mergefunc,globaldce`,
   cross-member inlining, one backend) -- text -0.2%, mistune's hot path 0.0%, and a
   serial backend over the merged module (22 s for pydantic, 6.4 s for mistune, where the
   members' backends now run in parallel); identical-code folding (`lld --icf=all` over
   function sections) -- -0.3% text, and only with lld, which `cc` does not use; function
   and data sections with `--gc-sections` -- -0.4% (function sections now ship anyway, for
   the backend's speed, PR #37); hot/cold splitting of error paths
   (`hotcoldsplit`) -- text -0.8% but `.eh_frame` +33%, hot path +0.13% instructions and
   +1.3% L1i misses; `minsize` module bodies -- text -50 KB, `.eh_frame` +70 KB, import
   +0.1%; `cold` on the shim's import-only C functions -- no measurable change;
   `nounwind` generated code (`.eh_frame` -22%) and `--strip-all` (-1.57 MB, the symbol
   table, which no loader maps) -- smaller files, but no unwinding through or naming of
   compiled frames in debuggers and profilers; `-z noseparate-code` -- 4 KB for an
   executable read-only segment. Where pydantic's bytes are: `.text` 4.41 MB (generated
   functions 1.42 MB, module bodies 0.92 MB, wrappers 0.55 MB, runtime 0.44 MB, the
   per-member C units 0.30 MB -- the remaining identical code, which takes moving them
   into the runtime unit over the module record), `.rodata` 3.49 MB (1.32 MB of fallback
   chunk tables and the fallback source), symbol tables 1.57 MB.
3. **Less work at import:** fewer fallback chunks executed at import (functions and classes
   created natively where possible), and lazy creation of module-level objects only where
   it is unobservable to Python code (module `__dict__` contents, `dir()`, `inspect`,
   pickling, import side-effect order and exceptions match CPython); every laziness rule is
   documented with its observability argument and covered by oracle tests.
4. **General, not pydantic-only:** mistune's and pystache's import times are measured in
   the CI benchmark job and are no slower than CPython's; no package check regresses.
   **Progress 2026-10-30:** `bench/package_check.py --time` times `import mistune` and
   `import pystache` (`import_timed`: one import per fresh `-I` process, nothing imported
   before it but the interpreter's startup modules, the CPython tree from the `.pyc` files
   its warm-up run wrote, interleaved with the compiled tree and the Cython and mypyc
   trees that pass the suite; median and min-max), so `bench.yml` publishes both.
   **Measured 2026-10-30:** bench run 41069474310 at 683411e (11 interleaved runs,
   median (min-max), CPython / compiled): x86_64 (AMD EPYC 9V45) mistune 19.02 ms
   (18.92-19.78) vs 19.64 ms (19.37-20.06), **0.97x**; pystache 6.40 ms (6.32-6.50) vs
   8.09 ms (7.96-8.14), **0.79x** (Cython 7.09 ms); aarch64 (Neoverse-N2) mistune 28.53
   ms vs 29.21 ms, **0.98x**; pystache 9.53 ms vs 11.94 ms, **0.80x** (Cython 10.59 ms).
   Not met yet: both are slower than CPython (the baseline below says why; pystache's
   largest gap is `compile()` at import, lever 1). mypyc builds neither (mypy errors);
   Cython's mistune fails mistune's suite, so only pystache has a Cython column.

## Progress: accept 3's levers

Each lever's own-share instructions, measured as the baseline's (Ubuntu 3.13.16,
callgrind, own share), after the lever and the ones before it. CPython's own share on
this host: pystache 7.64M, mistune 28.99M, pydantic 88.45M; the baseline's compiled
pystache 15.68M, mistune 28.88M, pydantic 102.38M.

| lever | change | pystache | mistune | pydantic |
|---|---|---|---|---|
| 1 | no `compile()` at import: the class maker in C (`src/ext/module/class_maker.c`), a published class's arguments evaluated from a build-time plan when they are bare names, the frames probe's template made with `types.CodeType` | 10.52M (-5.16M) | 25.95M (-2.93M) | 99.67M (-2.71M) |
| 2 | compiled frames' code objects made cheaper, still at first use: `co_filename`'s `dirname`/`join` done in C on POSIX instead of through `os.path`, the code object made by `types.CodeType(...)` with positional arguments instead of `code.replace(**changes)`, a module's `__builtins__` its builtins' dict (as `exec` stores it) instead of an import of `builtins` | 10.11M (-0.42M) | 25.14M (-0.81M) | 98.52M (-1.15M) |
| 4, 7 (finder) | one `__import__` per `from m import a, b` statement, as CPython: the first name's call imports and keeps the module for the statement's next names (`src/ext/module/import_io.c`); the package finder takes `ModuleSpec` from the frozen import system already in `sys.modules` instead of importing `importlib.machinery`, which loaded `importlib` and three of its modules a source import does not | 9.17M (-0.94M) | 24.97M (-0.17M) | 97.54M (-0.98M) |

Lever 1 also drops the `sys.__pycc_frame_template__` attribute the probe shared its
template through, so the import adds nothing to `dir(sys)`, as CPython's does
(`tests/v011_import.rs`). Arguments other than bare names (`Generic[T]`, which
pydantic's public classes do not use) are still compiled from their source at import;
a class statement with a keyword or a dotted base runs in CPython and makes no
published class.

Lever 2 is not the lazy code objects the plan named: a compiled frame is a real
`_PyInterpreterFrame` linked on the thread's chain whenever compiled code runs a
module body or a function whose frame Python code can see, and CPython reads its
`f_executable` there itself (`sys._getframe`, `warnings` and `tracemalloc` walking the
stack, profilers, `inspect`), so the code object must exist before the frame is linked,
not when one of those first asks for it. What lever 2 removed is the cost of making
each one (47 at pydantic's import, mostly module bodies): 36K instructions each before,
11K after. A module's `__builtins__` is now the dict CPython's `exec` stores, where the
compiled module stored the `builtins` module (`tests/v011_import.rs` checks both).

### Method

- Trees: `python3 bench/pydantic_check.py --keep DIR` (the compiled pydantic 2.13.5 but
  `pydantic.v1`, whole-package `--ext --non-strict --release`; its `.py` files then
  removed), the unchanged sdist for CPython; mistune 3.3.4 and pystache 0.6.8 from
  `python3 bench/package_check.py mistune pystache --time --keep DIR` (`DIR/<pkg>/cpython`
  and `DIR/<pkg>/compiled`). One discarded run per tree writes the `.pyc` files first.
- The measured process: `python3 -P -s imp.py TREE PKG`, where `imp.py` puts `TREE` first
  on `sys.path`, runs the import (`import pydantic; from pydantic import BaseModel`, or
  `import mistune` / `import pystache`), checks `PKG.__file__` is under `TREE` and ends
  with `os._exit(0)` (no interpreter teardown: the timed workload stops at the end of the
  import). `PYTHONHASHSEED=0`, no other `PYTHON*` variable (as `--instructions` runs).
- Count: `valgrind --tool=callgrind --callgrind-out-file=OUT python3 -P -s imp.py TREE
  PKG` (valgrind 3.22) less the same process importing nothing. **Own share:** both
  processes first import every module the package's import loads that is not the
  package's own (81 for pydantic: the stdlib, pydantic-core, typing-extensions, ...; 53
  for mistune, 22 for pystache; listed by diffing `sys.modules` around a CPython import),
  so the difference is the package's own modules.
- Totals use Ubuntu's `python3.13` 3.13.16 (stripped). The per-function breakdown uses
  python-build-standalone 3.13.13 (`uv python install 3.13.13`: a shared, unstripped
  libpython like CI's setup-python; pydantic-core 2.46.5 and its other dependencies from
  `.github/bench-requirements.txt`); its totals are 5-8% below Ubuntu's and its gaps the
  same. Per-function costs are `callgrind_annotate --inclusive=yes` for an entry point
  that does not recurse (the inclusive cost of a recursive one, such as a module's exec
  slot, counts nested imports), and the own share is the difference of the two files.
- Counts of objects and events: `sys.addaudithook` around the import (`exec`, `compile`,
  `marshal.loads` with its byte count, `code.__new__`, `function.__new__`), and
  `gc.get_objects()` by type before and after it. Load cost: `LD_DEBUG=statistics`,
  `readelf -rW`, `size -A`, `getrusage` minor faults and `/proc/self/status` `VmRSS`
  around the import; per module, `python3 -X importtime` self times (median of 15).
- `perf` cannot run here (no `perf` build for the VM's kernel); `PYCC_TIME=1` times the
  build's phases, not the import, so neither is used.

### Levers, ranked by estimated savings

Estimates are pydantic's / mistune's / pystache's own-share instructions, from the rows
above. Tier 1 is pycc's own overhead (accept 1's 1.0x, accept 4); tier 2 is work CPython
does too (accept 1's 1.2x, accept 3). Every lever keeps what Python code can observe;
where it is visible today (rows 9-11) it moves closer to CPython.

Tier 1 (together ~11.4M of pydantic's 13.1M gap; the rest is more of the module bodies run
natively):

1. **No `compile()` at import** (row 2): ship the class maker as a precompiled code object
   (or write it in C), make a public class's arguments from its statement natively or
   from a precompiled chunk, precompile the probe. -2.7M / -3.0M / **-5.3M** (pystache's
   largest gap: alone it brings its own share from 14.49M to ~9.2M).
2. **Ship less code in the chunk tables** (row 1): 1,479 code objects where the `.pyc`
   has 872 -- a forwarder and a signature wrapper per compiled function, each chunk its
   own module-level code object. Fewer, smaller code objects (one per class statement, a
   forwarder's body without its own constants and line table, the wrappers' factories
   merged), or native forwarders where a Python function is not required. -2M to reach
   the `.pyc`'s size, more as forwarders shrink.
3. **Forwarder patching from build-time indices** (row 3) instead of walking each class by
   qualified name. -1.5M / -0.5M / -0.2M.
4. **Compiled frames' code objects made when a frame is observed** (row 5: a traceback,
   `sys._getframe`, `inspect`), or precompiled, not on a function's first call.
   -1.6M / -1.1M / -0.55M.
5. **Imports** (rows 7, 10): one `__import__` per `from` statement, as CPython (an
   `__import__` hook then sees what it sees under CPython), and cached module references
   for the runtime's own `PyImport_ImportModule` lookups. ~-1.0M.
6. **Literal `str`s from a per-site slot** (row 6), not a hashed map. ~-1.0M / -0.3M /
   -0.07M.
7. **Smaller extension, fewer relocations** (row 4, accept 2): LTO across the package,
   identical-code folding, cold sections, packed relative relocations (`.rela.dyn` is 0.5
   MB). -0.5M instructions and part of the 455 extra page faults and ~1.2 ms of the
   package module's self time.
   **Done 2026-10-30** for what pays (accept 2): packed relative relocations and a cold
   module body; `dlopen` -0.05M (the relocations were cheaper than estimated); LTO,
   identical-code folding and hot/cold splitting did not pay.
8. **No `__pycc*` names in module dicts** (row 11; 405 builtins in pydantic's): they are
   visible to `dir()` and `vars()` (accept 3 must remove them anyway) and cost their
   objects and dict inserts. ~-0.5M.
9. **Signature publication by index** (row 8), not a `strcmp` scan per publication.
   ~-0.3M.
10. **The finder's `ModuleSpec` without importing `importlib.machinery`** (row 9; the
    frozen `_frozen_importlib` has it), so `sys.modules` matches CPython's. ~-0.3M /
    - / -0.3M.

Tier 2 (accept 1's stretch, accept 3):

11. **Run-time compiled source** (35.3M, 39% of CPython's own share): pydantic's 25
    dataclasses and 68 `ForwardRef`s compile source at every import. Intercepting
    `exec`/`compile` is observable (`builtins` identity, audit events), so the route is
    compile-time knowledge: a dataclass of a compiled module whose generated methods the
    build can produce exactly (`__init__`, `__repr__`, `__eq__`, ... with the
    `__qualname__`, `__code__` attributes and audit events CPython's have), and string
    annotations resolved without `compile()` where the result is the same. Up to -30M;
    feasibility unproven, the largest lever.
12. **Classes created natively or lazily** (175 class statements, 50.9M with the above):
    the class statements CPython runs today, created from build-time layouts; lazily only
    where accept 3's observability rules allow.
