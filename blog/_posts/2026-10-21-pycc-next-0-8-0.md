---
title: "pycc-next 0.8.0: I tried to make library code faster than CPython. It isn't."
---

0.8.0 is out. Its one big goal was **library code faster than CPython**: take pydantic,
compile it, and beat the interpreter running its sources. **That goal is not met.** Two of
five accept items are met, three are not, and this post is mostly about *why* -- because
the why decided what v0.9 is.

## 🏁 The scorecard

| goal | target | result |
|---|---|---|
| 1. pydantic faster than CPython | import >= 1.0x, define/schema >= 1.3x | ❌ **not met**: import 0.96x, define ~0.75x, schema ~0.8x; the 1.3x bar withdrawn with analysis |
| 2. common fallback constructs compile | `...`, local `import`, nested `def`, `lambda`, `hash()`; >= 1000/1249 native | ✅ **met**: 1029/1249 functions native, no forwarder frame |
| 3. compiled frames are real frames | `sys._getframe`, tracebacks; pydantic suite clean | ✅ **met**: **0** failures (was 20) |
| 4. a fourth package >= 2x | a Markdown or template engine | ❌ **not met**: mistune ~1x, pystache 0.69x |
| 5. Windows parity + corpus | `\r\n` stdout; strict >= 193/200 | ½ Windows ✅, corpus ❌ **191/200** |

## 🧪 The experiment, and the numbers

pydantic 2.13.5, built `--ext --non-strict`, the same pydantic-core wheel for both trees,
median of interleaved fresh-process runs (`bench/pydantic_check.py --time`, shared 4-core
Xeon, recorded 2026-10-21):

| phase | CPython | compiled | speed vs CPython |
|---|---|---|---|
| import | 86.8 ms | 90.4 ms | ❌ **0.96x** (0.40x in 0.7) |
| model definition | 8.75 ms | 12.30 ms | ❌ **0.71x** (0.70x) |
| `model_json_schema()` | 16.64 ms | 20.59 ms | ❌ **0.81x** (0.70x) |
| round-trips | 18.71 ms | 20.46 ms | ❌ **0.91x** (0.91x) |

Import went from 0.40x to 0.96x -- that's real progress. The rest barely moved. And here's
the number that explains everything:

**pydantic's define + schema, one repetition, under callgrind: 154.8M instructions
compiled, 151.2M for CPython.** Instruction parity. I got there lever by lever --
CPython 3.13's attribute specializations rebuilt as runtime caches (a cached `o.x` costs
**4.5 ns**, CPython 15.8), set displays built once per site, methods loaded before their
arguments. And it's *still* 0.8x on the clock.

Why? **The compiled tree misses the instruction cache more**: 0.88M L1i misses per define
round against CPython's 0.62M, D1 0.41M against 0.32M. Feed cachegrind's counts into a
cycle model and it predicts **0.83x** -- exactly what the stopwatch says. CPython's
specializing interpreter is already inline-cached C, hot and compact. My compiled code
does the *same* object operations -- `getattr`, dict reads, calls on objects a metaclass
built -- through ~43M instructions of its own helpers, spread over a bigger footprint.

To hit even 1.0x, that ~43M would have to drop under ~10M while libpython's share stays
fixed. That means **the object operations themselves would have to disappear**. pydantic's
definition code is metaclass- and dict-driven; an ahead-of-time compiler can't make those
operations go away. So I withdrew the 1.3x bar, wrote the analysis into the roadmap, and
moved on. No lever left in this architecture reaches it.

## 📝 Markdown and templates: the same wall

Accept 4 wanted a fourth package, another domain, **>= 2x**.

**mistune 3.3.4** (a Markdown engine, 38 modules): builds unchanged, its 1155 tests pass,
and it runs **58.0M instructions per `mistune.html` pass against CPython's 57.2M**. About
1x. Before building native classes for every parser, I ran an experiment: I hand-edited
mistune so `BlockParser` compiled as a fully native class. Result: **63.45M vs 63.48M --
it saved 0.03M instructions.** The parser isn't where the time goes. The time is in
CPython objects the parse builds and reads -- token dicts, `re` match objects, and about
11.6M in `re` itself.

So I needed a second candidate, and I picked it **by a rule fixed before measuring**: the
most-downloaded pure-Python template engine that has no C acceleration, interprets
templates in its own code (not generated Python), and ships its tests in the sdist. Jinja2
and Mako fail that, chevron ships no tests -- **pystache 0.6.8** wins. Disclosure: before the
rule was fixed I had timed chevron once and profiled pystache once under CPython; neither
run chose the package.

pystache: 255 tests pass compiled, 105 of 111 functions native, and its own benchmark runs
at **0.69x**. Same story: context-stack lookups, `re` matches, dict displays. Object work,
done at roughly the interpreter's cost and no less.

## 🧱 What did ship

The speed goal failed. The engineering under it is real, and v0.9 stands on it:

- 📦 **Whole-package builds.** `pycc build PKG --ext` compiles every module of a package
  into **one `.so`**: one runtime copy, one `dlopen`, each module still its own module
  object (own `__name__`, globals, `__spec__`, reload, circular imports) via the
  extension's own `sys.meta_path` finder.
- 🔗 **Native calls across modules.** A call into another module's compiled function goes
  straight to it, guarded by a single dict-version check. Microbench, 2M calls:
  **0.69 s -> 0.05 s**. Instances of another module's classes are read natively too.
- 🖼️ **Real CPython frames for compiled functions.** On 3.13, compiled code runs in genuine
  `_PyInterpreterFrame`s: `sys._getframe(n)`, `inspect.stack()`, `warnings`'
  `stacklevel`, and tracebacks with CPython's lines and carets. **pydantic's own suite:
  0 failures** beyond its sources (was 20).
- ⚡ **Attribute caches mirroring CPython 3.13's specializations**: instance values, slots,
  properties, methods, module attributes, each with `LOAD_ATTR`'s own guards, layouts
  checked at first use.
- 🧬 **pydantic 1029/1249 functions native** (809 in 0.7): `...`, function-local `import`,
  nested `def`, `lambda` and `hash()` compile, and methods of CPython-created classes call
  their compiled bodies with no forwarder frame.
- 🪟 **Windows stdout parity**: native programs write CPython's text-mode streams --
  `\r\n`, console UTF-8, `PYTHONIOENCODING`, the ANSI code page, CPython's error handlers
  and `UnicodeEncodeError`.
- 📐 **Shaped lists**: strict mode types `[name, index]` as a list of a fixed shape. Corpus
  strict 190 -> **191/200**; the nine left are programs `mypy` rejects too, and I won't
  weaken strict typing to count them.

## ⚡ Benchmarks

Fresh run on the release commit, `python3 bench/run.py`, best of 7, shared 4-core Xeon
2.1 GHz, Linux x86_64:

| program | CPython | pycc-next | Rust | vs CPython | vs Rust |
|---|---|---|---|---|---|
| collections_bfs | 0.818s | 0.113s | 0.050s | **7.2x faster** | 2.25x slower |
| fib | 0.200s | 0.011s | 0.007s | **18.4x faster** | 1.49x slower |
| mandelbrot | 1.177s | 0.039s | 0.031s | **30.6x faster** | 1.26x slower |
| nbody | 2.220s | 0.065s | 0.025s | **34.2x faster** | 2.63x slower |
| prefix_sum_np (kernel) | 2.669s | 0.031s | 0.015s | **87.5x faster** | 2.08x slower |
| sieve | 1.090s | 0.058s | 0.020s | **18.9x faster** | 2.86x slower |
| spectral_norm | 0.884s | 0.013s | 0.010s | **66.2x faster** | 1.35x slower |
| stencil2d (kernel) | 3.173s | 0.007s | 0.003s | **462.1x faster** | 2.24x slower |

Typed code: **18-66x** faster than CPython, as before (spectral_norm and collections_bfs a
little faster than in 0.7; on a shared machine, treat under ~20% as noise). Windows is not
benchmarked.

## 💡 The lesson

Put the two halves of this release side by side. Code over **typed native data** runs many
times faster than CPython: diff-match-patch and pypng compile to ~12x. Code over **CPython
objects** runs at about CPython's speed, however cleverly it's compiled. Compiling the
*code* was never the bottleneck. The *data* is.

## 🔭 Next: v0.9 -- typed hot data, native end to end

v0.9 goes after the data: a package's own classes, and the lists and `str`-keyed dicts its
compiled code builds, become **native values** that every module of the package reads
directly, with a guarded object fallback where they escape to CPython. The targets:
**pystache >= 2x**, **mistune >= 1.5x**, **pydantic no slower in any phase**, and strict
mode refusing *exactly* what `mypy --strict` refuses. Those are goals, not results -- I'll
report them the same way I reported these.
