---
title: "pycc-next 0.9.0: I made pystache's classes native. It's still 0.74x."
---

0.9.0 is out. The plan for v0.9 was simple: 0.8 proved the speed lives in **typed native
data**, so make libraries' hot data typed and native -- their own classes, lists and dicts
-- and watch the template engine, the Markdown engine and pydantic speed up. **Two of five
accept items are met. The three speed goals are not.** This post is about what shipped,
and about why a 25% cut in instructions bought almost nothing on the clock.

## 🏁 The scorecard

| goal | target | result |
|---|---|---|
| 1. native hot state in `--non-strict` | a package's own classes, lists and dicts native; `Generic[...]`, class-body lambdas, cross-module bases | ✅ **met** in its stated exact form (cross-module subclass = CPython class over the native base's layout) |
| 2. template engine | pystache >= 2x CPython | ❌ **not met**: **0.74x** (586k vs 505k instructions per round) |
| 3. Markdown | mistune >= 1.5x | ❌ **not met**: about **1x** (0.86x-1.05x) |
| 4. pydantic no slower | every phase >= 1.0x | ❌ **not met**: import 0.91x-0.98x, define ~0.79x, schema ~0.8x, round-trips 0.94x |
| 5. strict = a type checker | strict refusals match `mypy --strict`, issues #8/#9 | ✅ **met**: 9 refusals, mypy rejects 8, the ninth passes only through `Any` |

## 🧱 What shipped

A lot of library code that used to be shipped off to CPython class by class now stays
native in `--non-strict`:

- 🧩 **Native closures.** A nested function with unannotated parameters used as a value --
  `map(get_text, parts)`, `return resolve`, `sorted(xs, key=step)` -- is a native closure
  over the variables it reads. It used to run its `def` in CPython on *every call* of the
  enclosing function.
- 📦 **`*args` and `**kwargs` of objects** keep a class native: a constructor
  `def __init__(self, a, *items)` binds Python's call exactly as CPython does, `TypeError`
  messages included.
- 🧬 **`Generic[T]` classes, made by CPython.** A published compiled class is now created
  when its `class` statement runs, by its metaclass, from its real bases and a **compiled
  template** carrying its methods and layout. CPython runs the class machinery (MRO,
  `__init_subclass__`, `__mro_entries__`), so `class Box(Generic[T])` is native and Python
  sees `Box[int]`, `__parameters__`, `__orig_bases__`. Lambdas in class bodies too.
- 🐍 **Python subclasses of compiled classes.** `class S(m.C)` in Python code used to raise
  `not an acceptable base type`. Now it works, and when *compiled* code calls a method the
  Python subclass overrides, **the override runs**.
- 🐛 **A real bug, fixed by per-class dispatchers.** A subclass instance reaching compiled
  code typed as its base ran the **base's** methods: `show_it(Derived(3))` printed `base3`,
  CPython prints `derived3`. A method call whose class has an overriding compiled subclass
  now goes through one dispatcher per (class, method) that tests the run-time class. A
  class nobody overrides pays nothing.
- ⚡ **Call-site method caches.** `node.render(engine, context)` on a node read from a
  list: a hit is two compares and a direct call of the compiled method.
- ✂️ **Native `html.escape` and `re.escape`**, identity-guarded so a monkeypatched callee
  still gets called, with CPython's exact results.
- ✅ **`mypy --strict` parity in CI.** Every program strict mode refuses must be rejected by
  mypy too, or be listed in `DEVIATIONS.md` with a reason.
- 🪟 **Native class publication fixes** (issues #8, #9): a non-strict native build publishes
  its compiled classes in `__main__` like `--ext` modules do, so one module-level
  statement no longer sends every class to CPython.

## 🧪 pystache: the number that hurts

pystache 0.6.8's own benchmark, instructions per round (callgrind, steady state):

| step | compiled | CPython |
|---|---|---|
| start of v0.9 | 783k | 505k |
| `*args` + native closures | 611k | 505k |
| `html.escape`, 2-way attribute caches | 582k | 505k |
| templates, dispatchers, call-site caches | **586k** | 505k |

**783k -> 586k.** Python frames per round: **127 -> 40**. And the wall clock says
**0.74x** of CPython (median of 15 interleaved runs, today; 0.73x-0.94x across earlier
v0.9 runs on a loaded machine). Why so little?

1. **The floor is CPython's, not mine.** Of CPython's 505k instructions per round, about
   **158k** is regex searches, `match.start/end/groupdict` and `re.compile`'s cache lookup
   of a ~300-character pattern. No compile of pystache removes that. 2x means <= ~252k per
   round, so *everything* the compiled code does itself would have to fit in **~94k**. It
   spends ~428k.
2. **That 428k is crossing the boundary, not computing.** Method calls on objects, `str`
   copies at each crossing into CPython, context lookups through CPython dicts and
   `getattr`, the last Python frames.
3. **Instruction cache.** The hot code is the runtime's generic object-call paths plus the
   C API they enter: measured during v0.9, 21.0k L1i misses per round against CPython's 8.2k. Building with `O2`
   or `Os` instead of `O3`, or without inline refcounting, changed **neither size nor wall
   time** -- the optimizer's output was never the problem.

Getting to 2x needs the template's data -- context stacks, parsed nodes, rendered parts --
to stay native *end to end*. That's a bigger change than v0.9.

## 📝 mistune and pydantic

**mistune 3.3.4**: suite passes compiled, `mistune.html` over every benchmark document
**0.86x-1.05x**, the full parser with every plugin **0.84x-0.97x** (15 interleaved runs,
twice, today). Its parsers derive from `Parser(Generic[ST])` with private members and its
renderers dispatch through `getattr`; those stay CPython classes.

**pydantic 2.13.5**, built whole, 1036 of 1249 functions native, suite clean. Medians of 21
interleaved fresh-process runs, measured twice today:

| phase | speed vs CPython |
|---|---|
| import | ❌ **0.91x-0.98x** |
| model definition | ❌ **0.78x-0.80x** |
| `model_json_schema()` | ❌ **0.77x-0.83x** |
| round-trips | ❌ **0.94x** |

One honesty note. Mid-cycle I recorded **import 0.85x**, against 0.8.0's 0.96x -- it looked
like a regression. So for the release I built **0.8.0 and 0.9.0 side by side and measured
them back to back**: 0.8.0 gave 0.92x and 0.97x, 0.9.0 gave 0.98x and 0.91x, and under
callgrind `import pydantic` costs **375.6M instructions vs 372.1M (+0.9%)**. It was noise
on a shared machine, not a regression. 11 runs weren't enough; 21, twice, against the old
build, were.

## 💡 What this teaches

Two releases in a row now say the same thing, louder. **Speed comes from typed code.**
Typed programs run 20-58x faster than CPython; typed native data in real packages
(diff-match-patch, pypng) about 12x. **Dynamic library code reaches roughly CPython
parity** -- 0.74x to ~1x -- even after its classes, closures and dispatch go native,
because the work that remains is object protocol and C-API crossings that CPython's
specializing interpreter already does in compact, cache-hot C.

So the direction is clear: the compiler pays off where types are known, and the job for
untyped library code is *correctness at parity*, not miracles. Beating CPython on a
library like pystache needs its data to never become a CPython object in the hot path --
that's a design question for the next milestone, and I'll write it down as a goal, not a
result.
