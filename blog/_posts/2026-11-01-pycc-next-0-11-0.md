---
title: "pycc-next 0.11.0: mistune now imports faster than CPython, pydantic is still 3% short"
---

0.11.0 is out. This milestone had one headline goal: **importing a compiled package should
be at least as fast as importing its sources.** For mistune, it is now: **1.04x faster
than CPython.** For pydantic, the goal I actually named, **it isn't.** The import is
**0.97x** of CPython's on x86_64 and **0.98x** on aarch64, so it is still about **3%
slower**. I'm shipping anyway, and here's exactly where it stands.

## 🏁 The scorecard

All speed numbers here come from
[bench run 41248409468](https://github.com/rotnov/pycc-next/actions/runs/41248409468)
on the release's code (main 6ab165e): AMD EPYC 7763 and Neoverse-N2 runners, median of 15
interleaved fresh-process runs for pydantic, 11 for mistune and pystache.

| goal | target | result |
|---|---|---|
| 1. pydantic import | >= 1.0x CPython (stretch 1.2x) | ❌ **not met**: **0.97x** x86_64, **0.98x** aarch64 |
| 2. smaller, faster-loading extensions | measure LTO, folding, cold code; ship what pays | ✅ **met** |
| 3. less work at import | fewer fallback chunks run at import, nothing lazy that Python can see | ✅ **met** |
| 4. mistune and pystache imports | no slower than CPython | ✅ mistune **1.04x** / **1.03x**, ❌ pystache **0.97x** / **0.94x** |

## 📈 From 0.89x to 0.97x

At the start of the milestone, the same CI job had pydantic's import at **0.89x** (x86_64)
and **0.93x** (aarch64). Now:

| import | x86_64 CPython | x86_64 pycc-next | ratio | aarch64 CPython | aarch64 pycc-next | ratio |
|---|---|---|---|---|---|---|
| pydantic | 87.81 ms | 90.78 ms | **0.97x** | 70.89 ms | 72.13 ms | **0.98x** |
| mistune | 33.09 ms | 31.95 ms | ✅ **1.04x** | 28.29 ms | 27.38 ms | ✅ **1.03x** |
| pystache | 11.18 ms | 11.51 ms | 0.97x | 9.40 ms | 10.02 ms | 0.94x |

pystache moved the most: from **0.79x to 0.97x**. Most of its gap was `compile()` running
at import, and that's gone.

pydantic's other phases didn't move in this milestone, and they're not wins either: model
definition **0.81x** / **0.78x**, `model_json_schema()` **0.83x** / **0.82x**, round-trips
**0.91x** / **0.92x**.

## 🧱 What shipped

- 🚫 **No `compile()` at import.** The helper that builds published classes is now
  written in C. A class statement's bare-name arguments come from a plan made at build
  time, so the import doesn't compile any source for them.
- 🔑 **Interned names.** The import looks names up by interned `str` keys instead of C
  strings, which it used to decode and hash into a new `str` every time.
- 🪞 **Compiled import mirrors.** When fallback code reads names that a compiled `import`
  bound, compiled code now stores the values it got straight into the module namespace.
  It used to run the whole statement a second time. One `__import__` call, not two.
- ✂️ **Wrapper-less defs.** A fallback chunk made only of plain `def`s (constant defaults,
  no decorator, no closure) used to run as its own little code object in a frame of its
  own, just to make the functions. Now the functions are made directly from their code
  objects. That's **105 of the 443** chunk runs in pydantic's CI import.
- 🗜️ **Smaller extensions.** On glibc 2.36+ with a linker that supports it, extensions
  use packed relative relocations. pydantic's extension is **4.6% smaller**, and its
  relocation entries went from **21,222 to 349**. LTO, identical-code folding and hot/cold
  splitting were measured too. **They didn't pay, so they didn't ship.**
- 🔧 Plus cheaper forwarder patching, cheaper string-literal interning, one `__import__`
  per `from m import a, b` like CPython does, and a fix for a `for` loop that leaked its
  iterator on `return`.

## 🧪 Why pydantic is still 3% short

In instructions, the CI workload's pydantic import phase costs **212.67M against CPython's
208.77M** (callgrind). That's a **1.9% gap**, and there is no single big item left in it.
At the last breakdown, **nothing was above 0.75M instructions.** The gap is spread thin:

- unmarshalling the fallback chunk tables,
- the `str` literal cache,
- string hashing,
- relocations when the extension loads.

There's also a choice I made on purpose. **Decorated `def`s and class statements still
run as `exec`'d chunks.** A decorator or a class body can raise, and when it does, the
traceback has to look exactly like CPython's. Making them directly would cut the frame
CPython shows, so they keep the cost.

I also measured two ideas that didn't pay, and recorded them in the
[v0.11 roadmap](https://github.com/rotnov/pycc-next/blob/main/docs/roadmap/v0.11.md):
merging a module's chunks into one code object (saves about as much as its dispatch costs)
and shrinking the runtime's hashed caches (faster import, slower everything after).

## 🔭 What's next

v0.12 carries the two goals I missed: **pydantic's import >= 1.0x** (still 1.2x as a
stretch) and **pystache's import no slower than CPython's.** With no big item left, the
next gains have to come from many small ones, or from doing at build time work that
CPython itself does at every import.
