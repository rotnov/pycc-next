---
title: "pycc-next 0.12.0: compile less, win more. pydantic's schema is 1.2x CPython, its import still isn't"
---

0.12.0 is out, and it changes what a non-strict `--ext` build is. **I stopped compiling
whole modules.** A build now compiles only the functions that a `pycc profile` run
**measures as winners**, and everything else runs as CPython bytecode. The result:
pydantic's `model_json_schema()` went from **0.83x** of CPython in v0.11 (against
CPython 3.13) to **1.20x**
(x86_64) and **1.23x** (aarch64), and the whole pydantic process is **1.07x**. The
import, the goal I carried over from v0.11, is **still not above CPython: 0.99x.** And
two packages that the old whole-module builds made fast, **pypng and tomli, got slower.**
Here's all of it.

## 🏁 The scorecard

All speed numbers here come from
[bench run 43192816730](https://github.com/rotnov/pycc-next/actions/runs/43192816730)
on the release's code (main 5b7cc6c): CPython 3.15.2, AMD EPYC 7763 and Neoverse-N2
runners with 4 vCPUs each, median of 15 interleaved fresh-process runs for pydantic
2.14.2, 11 for the others. Ratios are CPython's time over pycc-next's: above 1, pycc-next
is faster.

| goal | target | result |
|---|---|---|
| 1. pydantic import | >= 1.0x CPython | ❌ **not met**: **0.99x** x86_64, **0.99x** aarch64 |
| 2. pystache import | no slower than CPython | ✅ **met**: **1.01x** / **1.00x** |
| 3. pydantic `model_json_schema()` | >= 1.15x | ✅ **met**: **1.20x** / **1.23x** |
| 3. pydantic model definition | >= 1.0x | ✅ **met**, at parity: **1.00x** / **1.01x** |
| 3. pydantic whole process | >= 1.0x | ✅ **met**: **1.07x** / **1.07x** |
| 3. pydantic import stays >= 1.0x | >= 1.0x | ❌ **not met**: 0.99x / 0.99x, same as goal 1 |
| 3. mistune and pystache | no slower than before the switch | ✅ **met** |

One honest note on goal 3: the schema target was **1.2x** until the day of the release.
I lowered it to **1.15x**, because hand-written C for the three hottest functions, the
ceiling I measured before starting, only reaches **1.25x**. A 1.2x bar left no room for
noise. The result clears both.

Under callgrind, the schema phase now runs **561.33M instructions against CPython's
733.58M** on x86_64. That's real work removed, not a lucky timing.

## 📉 The losses

**pydantic's import is at parity, not above it.** 93.76 ms against 92.94 ms on x86_64,
74.40 ms against 73.91 ms on aarch64, inside the spread on both. That's by construction
now: the modules run as CPython bytecode, so the import does what CPython's does. To beat
it, I have to remove work CPython does at every import. **43% of the import phase's
instructions are CPython compiling text at run time:** `compile()` of 737 forward
references and `exec` or `eval` of 101 generated texts, 53 of them `dataclasses`
methods. A prototype that hands `dataclasses` code objects made at build time took the
import from 73.3 ms to 64.2 ms locally (**1.14x**). That's a local prototype, not a CI
number.

**pypng and tomli regressed.** In v0.11 they were built whole-module. Now they compile
only what their profiles select, and that's a lot less speed:

- pypng's five-filter read: **10.42x -> 2.02x** on x86_64 (17.20x -> 1.95x on aarch64);
- tomli's `loads`: **1.70x -> 1.42x** on x86_64 (1.49x -> 1.31x on aarch64).

They weren't targets of this milestone, but a regression is a regression. **Both are v0.13
goals.**

## 🧱 What shipped

- 🔬 **`pycc profile`.** It runs a workload against a package's sources, nothing compiled,
  and writes one JSON file: per function, calls, self time, callees, the exact argument
  types it saw, and a hash of its source. Then it builds the candidates and **times them
  against CPython.** Only a set that wins gets compiled.
- 🧮 **Instructions, not stopwatches.** Fresh-process wall times of a test suite vary by
  about 15% from run to run, so a set that saves a few percent was a coin toss (pypng's
  selection flipped between 8 and 30 functions). Pass 3 now decides on callgrind
  instruction counts when it can, which repeat to a few instructions in billions.
- ✂️ **Pruning the winner.** Pass 3 tries dropping each member of the winning set. For
  pydantic it went from 9 functions to 6, and the 6 run fewer instructions than the 9.
- 🎯 **Typed copies where they pay.** A selected function gets a native copy typed with the
  exact types the profile observed, behind an exact-type guard, but only for parameters
  a loop actually computes with natively.
- ⚡ **Idiom lowering in generic bodies.** `try: d[k] except KeyError` on a missing key
  makes no exception object, `for k, v in d.items()` in a comprehension walks the dict
  with `PyDict_Next`, `sorted()` of a generator sorts in place, and scanner positions stay
  machine words.
- 🗑️ **A lot deleted.** The chunk tables, the build-time dataclass texts and forward
  references, direct defs, `--exact-cpython` and `--select module` are gone. pydantic's
  whole-module extension (`--select all`) is 1.81 MB smaller for it.

## 🧪 Why this direction

v0.11 squeezed the "compile everything" model one cost at a time, and pydantic's
definition and schema phases stayed around **0.8x**. A headroom experiment showed why: the
compiled tree ran about as many instructions as CPython, but with **twice the
instruction-cache misses** from a 10.9 MB extension. Two big hot code bases fought over
one cache. Compiling only the hot functions, and compiling them well, removes the fight.
The schema phase is the proof. pypng and tomli are the cost, and I'm not hiding it.

## 🔭 What's next

v0.13 has three goals:

1. **pydantic's import >= 1.0x**, with build-time code objects for the texts CPython
   compiles at import (the 1.14x prototype).
2. **pypng and tomli no slower than before the switch**, relative to CPython, in the CI
   benchmark on both runners.
3. **Hold what v0.12 met**: schema >= 1.15x, definition and whole process >= 1.0x,
   mistune and pystache no slower than at v0.12.0.
